When we call an AI API, we usually take the provider at its word: the model answering our request is the one we selected. But a model name in an API response is only a label, and output quality is not reliable proof of identity. If a provider silently substitutes a different model, users have few ways to verify what happened.

**FlashProve**, an open-source research project released by Anthropic in November 2026, explores a cryptographic answer to this problem: enabling a model provider to prove that specified outputs are consistent with the computation of a previously committed model, without revealing its weights.

## 1. What FlashProve Does—and Why It Matters

FlashProve uses zero-knowledge proofs to implement a **commit–prove–verify** workflow.

First, the provider creates a cryptographic commitment to a specific set of model weights, fixing the model against which subsequent claims will be checked. The provider then generates a proof for a request and specified output positions. With the commitment, public configuration, request, output, and proof, a user can verify the claim on a CPU—without accessing the weights or rerunning the large model.

Its value lies in shifting part of the trust relationship from **“the provider says it performed this computation”** to **“the user can independently check a claim about that computation.”**

This could matter for model routing, independent evaluations, and inference audits. Customers want assurance that the model they paid for has not been replaced. Evaluators want confidence that the model they tested is the one actually deployed. Enterprises may also want verifiable computational records for important tasks.

Two boundaries are essential.

**First, proving a computation does not prove that an answer is correct.** A model can still hallucinate or give bad advice. FlashProve checks claims about model computation, not the truth of statements about the world.

**Second, a commitment is not, by itself, proof of a model’s advertised identity.** Users still need a trusted way to associate the commitment and public configuration with a particular model version. Otherwise, a provider could simply commit to a different set of weights.

The approach is not limited to open-weight models. A closed-weight provider could generate proofs without publishing its weights. However, **the proving party must have access to the weights and be able to execute the corresponding computation**. An API intermediary with access only to an upstream service cannot independently add these proofs to the responses it receives. It can forward proofs if the upstream provider supplies them.

## 2. Where It Stands Today—and Whether It Is Ready for Commercial Use

Two questions should be separated: **does the license permit commercial use, and is the implementation ready for production?**

FlashProve’s code, documentation, and Lean proofs are released under Apache 2.0, which permits commercial use subject to its terms. Model weights remain subject to their own licenses. But commercial licensing does not establish production-grade security, reliability, or economics.

As of November 4, 2026, Anthropic describes FlashProve as intermediate research progress, and the repository explicitly labels it as a research artifact that is **not maintained and not accepting contributions**.

The project nevertheless demonstrates meaningful engineering progress. Using a public 4-bit conversion of Llama 4 Maverick, it performs proof generation for a large model on a single H100 GPU. Its performance figures, however, require careful interpretation:

- **Approximately 110 tokens per second** refers to post-hoc, batched prefill proving throughput—not real-time answer generation. In the main benchmark, each request contains a 1,024-token window, while its proof checks the next output token.
- **The average proof is approximately 18.78 MB.** At a batch size of 24, proof release takes roughly 221–226 seconds from the start of the batch, excluding queueing and service-side verification.
- **Reported proving GPU time is approximately 70–95 times the vLLM baseline.** This is a GPU-time comparison under specific configurations, not a direct measurement of total service cost.

Cost and latency are not the only obstacles.

The current implementation focuses on a particular mixture-of-experts model shape and a 1,024-token window. Its strict, exact-match policy checks whether an output token is the committed integer model’s top choice. It does not directly cover arbitrary floating-point inference or sampled outputs. More permissive acceptance policies are available, but **showing that an output falls within score-gap limits is not equivalent to proving that the model would generate that exact output**.

The security guarantees also need to be read precisely. FlashProve includes formal protocol definitions and security theorems in Lean, but these do not provide end-to-end formal assurance for the high-performance C++ and CUDA programs. Protecting secret weights additionally depends on demanding operational and state-management requirements. Independent security auditing and evidence of long-running service reliability remain insufficient.

**Our assessment is that FlashProve is suitable for research, reproduction, and controlled proofs of concept—not as the sole trust foundation for a production commercial service.** Asynchronous auditing and narrowly scoped pilots may be worth exploring, but they require further security assessment, engineering work, and economic validation.

## 3. TokHive’s Perspective

FlashProve points toward an important direction: trust in AI services does not have to rest entirely on API labels and provider assurances. It can increasingly be supported by independently verifiable computational evidence.

But FlashProve is not yet a ready-made verification switch for arbitrary AI APIs. Proving model computation and verifying an intermediary’s request-and-response handling address different layers of trust. They can complement each other, but neither substitutes for the other.

**TokHive will continue to follow advances in verifiable inference, zero-knowledge proofs, and trusted execution—evaluating their security, compatibility, and cost trade-offs, and exploring where they can meaningfully improve real-world AI services.**
