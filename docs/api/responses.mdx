# Responses

```http
POST /v1/responses
Authorization: Bearer <your key>
Content-Type: application/json
```

OpenAI's Responses API, served by ChatGPT subscriptions. Official SDKs work by pointing their base URL at `https://api.tokhive.ai/v1`.

```sh
curl https://api.tokhive.ai/v1/responses \
  -H "Authorization: Bearer $TOKHIVE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"gpt-5.5","input":"Reply with exactly OK."}'
```

```python
from openai import OpenAI

client = OpenAI(base_url="https://api.tokhive.ai/v1", api_key=TOKHIVE_API_KEY)
response = client.responses.create(model="gpt-5.5", input="Reply with exactly OK.")
print(response.output_text)
```

Both streaming (`"stream": true`) and non-streaming calls work. A non-streaming call runs as a stream upstream, and TokHive returns the assembled `response` object once it has completed and been verified. In a stream, the final `response.completed` event is held back until the result is verified and settled.

## How requests are adapted

The subscription upstream accepts fewer fields than OpenAI's public API. So that common SDK calls work unchanged, TokHive adapts requests as follows:

- A string `input` becomes one user message. A missing `input` becomes an empty list, so a call with only `instructions` works.
- `store` defaults to `false`. TokHive does not keep responses, so `"store": true` is refused with `400`, and so is `previous_response_id`: send the conversation history in `input` instead.
- A `system` message in `input` is sent as a `developer` message.
- These tuning fields are removed, because the upstream refuses them: `temperature`, `top_p`, `top_logprobs`, `max_output_tokens`, `max_tool_calls`, `truncation`, `metadata`, `user`, `safety_identifier`, `prompt_cache_retention` and `background` (`"background": true` is refused with `400`). The names of removed fields are listed in the `X-Hive-Ignored-Params` response header. They have no effect; for example, `max_output_tokens` does not cap the output length.
- Any other unsupported top-level field returns `400` with `Unsupported parameter: '<field>'`, and the error's `param` names the field.

A request that needs none of this is forwarded byte for byte, which is the case for the official Codex client.

## Conversations

A conversation that carries the session headers Codex sends stays on the provider account that served it, which keeps the upstream prompt cache warm. When the history can move, for example after that account becomes unavailable, it continues on another account. When it cannot, the call returns `409 session_context_unavailable`.

## Codex

```http
POST /v1/codex/responses
```

The same pipeline as `/v1/responses`, but the body must already be in the subscription upstream's own format. TokHive forwards it without the adaptations above and without checking field names. The console's Codex setup guide points Codex here, together with the [Codex model catalog](models.mdx#codex-model-catalog).
